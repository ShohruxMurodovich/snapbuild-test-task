# снэпбилд — развитие лендинга

Тестовое задание на позицию Fullstack Developer: изучить действующий лендинг
[snapbuild.ru](https://snapbuild.ru/), воспроизвести его и встроить **пять новых секций** так,
чтобы они читались как естественное продолжение страницы, а не как вставка из другого шаблона.

Выбран расширенный вариант: воспроизведены все существующие блоки (шапка, первый экран,
логотипы клиентов, продуктовые блоки, возможности, сравнение, безопасность, роадмап, FAQ,
финальный CTA, подвал), новые секции вставлены между ними.

**Опубликованная версия:** https://shohruxmurodovich.github.io/snapbuild-test-task/
**Репозиторий:** https://github.com/ShohruxMurodovich/snapbuild-test-task

---

## Локальный запуск

```bash
npm install
npm run dev          # http://localhost:3000
```

Проверка ровно того, что уезжает на GitHub Pages (статический экспорт + basePath):

```bash
npm run build:gh
NEXT_PUBLIC_BASE_PATH=/snapbuild-test-task npm run preview   # http://127.0.0.1:4173/snapbuild-test-task/
```

Остальные команды:

| Команда | Что делает |
|---|---|
| `npm run build` | статический экспорт в `out/` (без basePath, для локальной проверки) |
| `npm run preview` | отдаёт собранный `out/` на `127.0.0.1:4173` |
| `npm run audit` | проверяет горизонтальный скролл, высоты секций, битые картинки, ошибки консоли на 1280 / 768 / 375 |
| `npm run screenshots` | скриншоты страницы целиком на трёх ширинах в `.screenshots/` |
| `npm run assets` | заново скачивает и уменьшает публичные ассеты исходного сайта |
| `npm run deploy` | сборка с basePath и публикация `out/` в ветку `gh-pages` |

`audit` и `screenshots` поднимают системный Chrome в headless-режиме и общаются с ним по
Chrome DevTools Protocol через встроенный в Node WebSocket — без puppeteer и playwright
в зависимостях (`scripts/lib/cdp.mjs`).

GitHub Pages отдаёт содержимое ветки `gh-pages`: `npm run deploy` собирает статику
с `basePath` и публикует туда `out/`. GitHub Actions не используется намеренно —
деплой из ветки не требует прав на запись workflow-файлов.

## Стек

- **Next.js 15** (App Router) со статическим экспортом (`output: 'export'`) — на GitHub Pages
  уезжает обычная статика, `basePath` подставляется из переменной окружения;
- **TypeScript** — тексты секций лежат в типизированных объектах в `src/content`;
- **CSS Modules + слой дизайн-системы в обычном CSS** — без UI-библиотек и Tailwind:
  токены и общие классы повторяют устройство исходного сайта (см. ниже);
- **@fontsource-variable/inter-tight** — самохостинг шрифта, никаких внешних запросов в рантайме;
- зависимостей в рантайме, кроме React, нет; `sharp` и `gh-pages` — только для скриптов.

```
src/
  app/                layout.tsx · page.tsx (порядок секций)
  components/
    layout/           Header · Footer · CookieNotice
    sections/         Hero Logos Process UseCases Compare Security Roadmap Faq Cta   ← воспроизведённые
                      Scenarios Integrations Pricing Testimonials DemoForm           ← новые
    ui/               Section · SectionHead · Button · MediaCard · icons
  content/            site.ts · original.ts (тексты исходника) · added.ts (новые секции)
  hooks/              useScrolled · useMediaQuery · useDragScroll
  styles/             tokens.css · base.css · design-system.css
scripts/              fetch-assets.sh · optimize-images.mjs · screenshot.mjs · audit.mjs · serve.mjs
```

Интерактивные секции — клиентские компоненты, остальные (первый экран, логотипы, продуктовые
блоки, интеграции, финальный CTA) рендерятся статически и не тянут JS.

## Как анализировалась стилистика исходного сайта

Смотрел не на скриншоты, а на то, как страница устроена: снял её CSS и разметку, вытащил
вычисленные стили через DevTools Protocol и пересчитал все размеры к макету 1440.

**Главная находка — способ размерности.** На сайте нет контейнера с `max-width`: все размеры
заданы как доля вьюпорта относительно фиксированной ширины макета —
`calc(N / 14.4 * 1vw)` на десктопе (макет 1440), `calc(N / 8.1 * 1vw)` на планшете (810),
`calc(N / 3.75 * 1vw)` на мобильном (375). Ограничения сверху нет: на 1920 заголовок
первого экрана 101px, на 2560 — 135px, то есть те же `76 / 14.4 * 1vw`. Я собрал это
в одну переменную, поэтому любой размер из макета пишется одинаково:

```css
:root {
  --du: calc(1vw / 14.4);              /* размер = calc(N * var(--du)) */
  --dux: max(1px, calc(1vw / 14.4));   /* фиксировано до 1440, дальше растёт */
}
@media (max-width: 1023px) { :root { --du: calc(1vw / 8.1) } }
@media (max-width: 767px)  { :root { --du: calc(1vw / 3.75) } }
```

Вторая переменная нужна из-за того, что часть величин в исходнике ниже 1440 задана
фиксированно (шапка, радиусы, отступы финального CTA), а выше 1440 растёт в тех же
пропорциях — `max()` держит их на месте до 1440 и отпускает дальше. Совпадение проверено
замерами на **1280 / 1440 / 1920 / 2560**: по 18 контрольным величинам (ширина и высота
шапки, размеры заголовков, отступы секций, радиусы, размер надписи кнопки) расхождений нет.

**Снятые токены** (`src/styles/tokens.css`):

| Токен | Значение |
|---|---|
| Фон страницы | `#f5f5f6` |
| Поверхности | `#fff` (карточки), `#fafafa` (FAQ), `#f5f5f7` (пилюли, плитки) |
| Текст | `#000` / `#5a5b62` / `rgba(0,0,0,.6)` |
| Линии | `rgba(0,0,0,.05)` · `.045` · `.1`, разделители в карточках `rgba(0,0,0,.06)` |
| Фирменный градиент | `linear-gradient(90deg,#ff6d3c,#ff6ba7 46%,#bb6dff)` — заливка текста CTA и рамок |
| «Аврора» первого экрана | `linear-gradient(157deg,#fff 17.71%,#ffcdb3 43.16%,#ffa4b6 58.2%,#ffb2e9 73.32%,#d4d6ff 90.8%,#fff 103.16%)` |
| Радиусы | карточка и плитка 20, панель 16, кнопка 12, пилюля 999 (до 1440 в пикселях, выше растут) |
| Заголовок секции | 52 / 500 / `line-height 1.2308` / `letter-spacing -1px`, на мобильном 32 |
| Ритм секции | `padding: 32 40 128` (96 у сравнения, безопасности и FAQ), заголовок и подзаголовок — в колонку с отступом 8 |
| Движение | `cubic-bezier(0.16, 1, 0.3, 1)`, аккордеон 367ms на открытие и 200ms на закрытие |

**Повторно использованные паттерны.** Новые секции собраны из тех же элементов, что и
исходные: пилюли-переключатели из «Возможностей», рамка фирменным градиентом из колонки
«снэпбилд» в таблице сравнения (`padding-box`/`border-box`), плитка 56×56 с радиальной
подсветкой из «Безопасности», градиентная заливка текста из CTA, карточка «картинка +
заголовок + текст» вынесена в общий `MediaCard` и используется и в продуктовом блоке,
и в блоке безопасности.

Отдельно — три вещи, которые **есть в дизайн-системе исходника, но на странице
не задействованы**, и я их применил:

- `dds-btn-group` — переключатель периода в тарифах, вместе с его бейджем скидки
  под градиентную заливку;
- `text-overline` (600 / `0.06em` / uppercase) — разделители смысловых частей
  в секции интеграций;
- `--dds-btn-shine-white` + `--dds-btn-ease` / `--dds-btn-dur` — участвуют в блике
  по надписи кнопки (см. ниже).

## Что удалось воспроизвести

- **Шапка** — фиксированная «стеклянная» пилюля `min(100% − 32px, 960px)` с `backdrop-filter`,
  состоянием при скролле (рамка + тень `0 6px 22px rgba(29,22,40,.055)`), бургером на планшете
  и мобильном, полноэкранным меню с каскадом пунктов, ловушкой фокуса, Esc и блокировкой скролла.
- **Первый экран** — карточка с «авророй», заголовок 76/600 в три строки с теми же переносами,
  скриншот приложения, приклеенный к низу карточки; появление повторяет исходник
  (текст 1800ms, CTA 1100ms с задержкой 420ms, медиа выезжает снизу с масштабом 0.975).
- **Логотипы клиентов** — статичный ряд с каскадом появления от 768px и бесконечная бегущая
  строка на мобильном (второй набор продублирован и скрыт от скринридеров).
- **Продуктовые блоки, возможности, безопасность** — включая двухуровневое переключение
  в «Возможностях»: пилюли форматов и список пунктов, который раскрывает описание, подсвечивает
  активную строку пастельным градиентом и меняет картинку в панели.
- **Таблица сравнения** — сетка на 6 колонок (`display: contents` у строк), колонка «снэпбилд»
  обведена градиентом через `mask-composite`, на мобильном — горизонтальный скролл с залипающей
  колонкой названий.
- **Роадмап** — лента с линией времени; пройденные пункты считаются по дате (в исходнике так же:
  пройдено 9 из 12, залито 8 колонок линии), перетаскивание мышью.
- **FAQ** — две колонки по четыре вопроса, раскрытие через `grid-template-rows: 0fr → 1fr`,
  поворот «плюса» на 45°, несколько пунктов могут быть открыты одновременно.
- **Финальный CTA и подвал** — «аврора» со слоем «пыли» (`mix-blend-mode: plus-lighter`),
  белая кнопка с градиентным текстом, три колонки ссылок и мобильные варианты почты.
- **Плашка про cookie** — с запоминанием решения в `localStorage`.
- **Анимации кнопок — как в исходнике.** Надпись залита двумя слоями: белым блеском
  на 400% ширины и фирменным градиентом; при наведении блик проезжает по тексту
  (`0.75s linear`, кадры `dds-btn-text-shine`). У тёмных кнопок — тот же приём, но
  тёмным проблеском по белому тексту (`dds-btn-text-sweep`). Нажатие — `scale: 0.975`,
  как у `.dds-btn:active` в оригинале.
- **Живой фон финального CTA.** Два размытых цветных «блоба» по краям и световой блик
  в центре медленно двигаются (`7s` / `8s` / `6s`, `ease-in-out infinite`) — именно из-за
  этого градиент в исходнике дышит. Под `prefers-reduced-motion` анимации выключаются.
- **Появление при скролле** — секции и каскад карточек внутри сеток на scroll-driven
  анимациях.
- **Смена картинки в «Возможностях»** — анимацией, а не `transition`: при переключении
  формата React монтирует другой набор `<img>`, и переход на свежем элементе не
  запускается. Картинки остальных форматов подгружаются в простое
  (`requestIdleCallback`), поэтому переключение вкладок мгновенное. На мобильном
  картинки перелистываются свайпом с кадрами `slide-in-next` / `slide-in-prev`.
- **Перекадрированные картинки под узкие экраны.** Для карточки «Гибкая конфигурация»
  и трёх карточек безопасности исходник отдаёт отдельные файлы под планшет и мобильный —
  подключены через `<picture>`, иначе центральный объект обрезается кадром 2:1.

**Расхождения, которые я сделал сознательно:**

- **Появление секций — на scroll-driven анимациях** (`animation-timeline: view()`), а не на
  `IntersectionObserver`. Так секция видима по умолчанию: если браузер не умеет `view()` или
  JS не выполнился, контент всё равно на месте. Первая версия была на observer'е — и во время
  проверки скриншотами обнаружилось ровно это: при быстрой прокрутке колбэк не успевал
  сработать и финальный CTA оставался прозрачным.
- **Шапка залипающая с состоянием при скролле.** В CSS исходника класс `is-scrolled` описан,
  и я его использую как задумано.
- **Горизонтального скролла нет ни на одной ширине.** У исходника на 375px документ шире
  вьюпорта (текст уезжает за край) — у реплики `scrollWidth === clientWidth` на 1280 / 768 / 375.
- **Мелкий текст не меньше 12px:** там, где плавающий размер уходил ниже, стоит
  `max(12px, calc(N * var(--du)))` — тем же приёмом, что в исходнике у почты в подвале.
- **Переносы текста.** В исходнике неразрывные пробелы расставлены руками
  (`Одна платформа&nbsp;— весь маркетинг`, `из&nbsp;одной идеи`). У реплики то же
  правило применяется ко всем текстам автоматически (`src/content/typography.ts`):
  короткие слова и тире не остаются в конце строки. До этого на странице висело
  16 предлогов на 1280px и 33 на 375px, сейчас — ноль.

## Что не удалось реализовать и почему

- **Шрифт.** Оригинал набран TT Commons Pro — это коммерческая лицензия, публиковать файлы
  в открытом репозитории нельзя. Подобрал замену по метрикам: измерил ширину заголовка первого
  экрана в TT Commons Pro (2312px в одну строку при 67.56px/600) и сравнил восемь бесплатных
  кириллических гарнитур. **Inter Tight** дал 2304px — расхождение 0.3%, поэтому переносы строк
  совпадают с оригиналом не только на первом экране. Onest, Golos Text и Inter шире на 4.8–6.9%
  и ломали вёрстку заголовков. В стеке TT Commons Pro стоит первым: если гарнитура установлена
  в системе, страница отрисуется именно ей, иначе подхватится Inter Tight.
- **Продуктовые изображения.** 3D-рендеры, скриншоты интерфейса и «пыль» для CTA — это ассеты
  снэпбилда; я их не перерисовывал, а взял публичные файлы с сайта (`scripts/fetch-assets.sh`)
  и уменьшил до 1920px (`scripts/optimize-images.mjs`): часть картинок отдаётся в 5760px,
  на макете 1440 это лишние 4.4 МБ. Все визуалы новых секций сделаны на CSS и SVG.
- **Внутренняя дизайн-система.** Слой `dds-*` — не публичный пакет, у меня был только
  собранный CSS. Я восстановил токены и паттерны по нему, но это реконструкция, а не та же
  система: имена классов и структура компонентов мои.
- **Backend у формы.** По условиям задания реальная отправка не требуется: форма валидирует
  данные, показывает состояние отправки и экран успеха, но никуда их не отправляет —
  об этом написано прямо под кнопкой.
- **Содержимое новых секций — демонстрационное.** Цены, отзывы и метрики я придумал под
  продукт. Цитаты специально **не** приписаны компаниям из блока логотипов: указаны только
  роль и обезличенное описание компании. В подвале об этом есть пометка.

## Что улучшил бы при большем запасе времени

- Разобрал бы шаблон «секция с горизонтальной лентой» на общий компонент: роадмап, таблица
  сравнения и полосы пилюль сейчас решают одну задачу тремя похожими способами.
- Сделал бы визуальные регресс-тесты: снимки на трёх ширинах уже автоматизированы
  (`npm run screenshots`), не хватает попиксельного сравнения с эталоном в CI.
- Добавил бы состояния для реальной отправки формы: серверную валидацию, ошибку сети,
  защиту от повторной отправки и honeypot от ботов.
- Прогнал бы страницу через axe и полный аудит Lighthouse; сейчас проверено вручную —
  клавиатура, `prefers-reduced-motion`, контраст, ARIA у табов, аккордеона, карусели и формы.
- Вынес бы тексты в MDX или CMS-подобный слой — сейчас это типизированные объекты, что уже
  удобно, но редактировать контент без разработчика всё равно нельзя.

## Какие AI-инструменты использовались

Работа сделана в **Claude Code (Opus)**, задачи распределялись так:

- **Анализ исходного сайта** — скачать CSS, разметку и скрипты, вытащить вычисленные стили
  через Chrome DevTools Protocol, пересчитать размеры к макету 1440, найти систему
  `calc(N / 14.4 * 1vw)` и составить таблицу токенов.
- **Подбор шрифта** — измерение ширины строки в восьми гарнитурах и сравнение с оригиналом
  вместо подбора «на глаз».
- **Вёрстка** — компоненты секций и CSS по снятым значениям, тексты новых секций.
- **Инструменты проверки** — скрипты `audit.mjs` и `screenshot.mjs` на CDP, скачивание
  и сжатие ассетов.
- **Проверка результата** — сравнение высот секций с оригиналом, прогон интерактива
  (табы, переключатель тарифов, карусель, аккордеон, мобильное меню, валидация формы),
  контроль горизонтального скролла и консоли на 1280 / 768 / 375.

Правки по итогам проверок вносились вручную: например, замена `IntersectionObserver` на
scroll-driven анимации, `height: auto` для картинок с `aspect-ratio` (атрибут `height`
перебивал пропорцию), раскладка шапки на мобильном и минимальные размеры мелкого текста.
